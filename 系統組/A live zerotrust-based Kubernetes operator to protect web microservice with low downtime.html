這個專題在做什麼

開發 Kubernetes Operator，依零信任原則持續監控微服務並自動套用隔離、憑證、網路政策或修復動作，同時降低服務中斷。

擬議摘要

本專題旨在處理以下問題：開發 Kubernetes Operator，依零信任原則持續監控微服務並自動套用隔離、憑證、網路政策或修復動作，同時降低服務中斷。 研究方法將依序定義 Custom Resource 與控制迴圈；接著串接 service mesh、NetworkPolicy 或身分驗證；接著以攻擊演練測安全效果、恢復時間與可用性。實驗應採固定資料切分或測試情境，將提出的方法與可重現的簡單基準比較，同時記錄主要品質指標、執行成本與失敗案例。預期成果包括可執行的端到端原型、可重建的實驗結果，以及對方法適用條件與限制的分析。

關鍵詞： 雲端原生系統、分散式系統、容器安全、可靠度工程

必修課程逐科主題與選題前檢核

程式設計（Python 或 Java/C++）

  • 應掌握的具體主題：變數、型別、控制流程與函式；模組化、例外處理與檔案 I/O；基本物件導向、套件管理、除錯與單元測試；Git 版本控制與可重現執行環境。
  • 選題前檢核：能從零完成一個讀取真實資料、處理錯誤、輸出結果且附測試的小程式。

資料結構

  • 應掌握的具體主題：陣列、鏈結串列、堆疊與佇列；雜湊表、樹、堆積與圖；走訪、搜尋、排序與記憶體／時間取捨；依資料存取模式選擇結構。
  • 選題前檢核：能解釋選用某資料結構的原因，並估算主要操作的時間與空間複雜度。

演算法

  • 應掌握的具體主題：漸近複雜度與正確性證明；分治、貪婪、動態規劃與回溯；圖搜尋、最短路徑、匹配與基本最佳化；建立基線、比較演算法與設計測試案例。
  • 選題前檢核：能為核心問題提出至少兩種方法，說明複雜度並用邊界案例驗證。

作業系統

  • 應掌握的具體主題：process/thread、排程與同步；虛擬記憶體、檔案系統與 I/O；system call、權限、隔離與資源限制；競態、死結、效能剖析與 Linux 操作。
  • 選題前檢核：能在 Linux 追蹤程序／記憶體／I/O，重現一個競態或資源限制案例並修正。

計算機網路

  • 應掌握的具體主題：TCP/IP 分層、封包、路由與 DNS；TCP/UDP、HTTP、TLS 與常見應用協定；延遲、吞吐、壅塞、重傳與封包分析；Socket、API、網路服務部署與基本威脅。
  • 選題前檢核：能寫 client/server、用 Wireshark 解釋一次連線，並定位延遲或封包錯誤。

資訊安全

  • 應掌握的具體主題：機密性、完整性、可用性與威脅建模；驗證、授權、最小權限與金鑰管理；常見網路／系統／Web 弱點與安全測試；日誌、事件回應、隔離實驗與負責任揭露。
  • 選題前檢核：能為專題畫出資料流與信任邊界，列出資產、攻擊者、攻擊面及對應控制。

詳細完成步驟

以下以一個 16–18 週學期專題規劃；需要人體研究、特殊硬體、臨床／產業資料或長期蒐集者，應在第 1 階段就延長時程。各階段都要留下可重現的程式、設定與結果。

  1. 第 0–1 週：與教授鎖定問題與邊界。 把題目改寫成一頁規格，明確列出使用者、輸入、輸出、不處理事項、成功指標與失敗條件。面談必須決定：要自動處置哪些具體威脅？ 低停機的 SLO 與回滾策略是什麼？
  • 完成門檻：教授確認書面 scope、可用資源、每位組員分工及倫理／授權限制。
  1. 第 1–3 週：通過先備能力檢核。 不只「修過」課，而要完成下列可展示的小任務：
  2. 完成「程式設計（Python 或 Java/C++）」的選題前檢核
  3. 完成「資料結構」的選題前檢核
  4. 完成「演算法」的選題前檢核
  5. 完成「作業系統」的選題前檢核
  6. 完成「計算機網路」的選題前檢核
  7. 完成「資訊安全」的選題前檢核
  • 完成門檻：把檢核成果放入同一個 Git repository，其他組員能依 README 重跑。
  1. 第 2–4 週：閱讀與基準盤點。 找 3–5 個最接近的方法、資料集或開源系統，整理它們的輸入、輸出、限制、授權與評估方式。先決定一個最簡單、可重現的 baseline，避免一開始直接做最複雜模型。
  • 完成門檻：一張方法比較表、一份引用清單，以及 baseline 的選擇理由。
  1. 第 3–6 週：建立資料／設備／環境。 以 Go、Kubernetes、Docker、Operator SDK、Istio/Cilium 建立固定版本環境；準備最小資料樣本、資料字典、切分規則與設備清單。若涉及個資、人體、醫療、攻擊或平台內容，先完成同意、去識別、隔離與授權程序。
  • 完成門檻：新電腦可依腳本建立環境，並從原始輸入跑到一筆可檢查的輸出。
  1. 第 4–7 週：完成端到端 baseline。 用最簡單可行方法串起輸入、處理、輸出與評估；先記錄速度、資源與主要品質指標，這會是後續改進的比較基準。
  • 完成門檻：固定測試集上的第一份結果表、至少 10 個人工檢查案例，以及已知失敗清單。
  1. 第 6–12 週：實作題目核心。 依序完成：
  2. 定義 Custom Resource 與控制迴圈
  3. 串接 service mesh、NetworkPolicy 或身分驗證
  4. 以攻擊演練測安全效果、恢復時間與可用性
  • 每完成一項就加自動測試、實驗設定與中間產物版本；若兩週沒有勝過 baseline，立即縮小範圍或改方法。
  1. 第 10–14 週：做公平而可重現的評估。 以「以攻擊演練測安全效果、恢復時間與可用性」為主軸，預先固定資料切分、主要／次要指標與比較方法；加入 ablation、效率量測、信賴區間或重複實驗，並按場景切片做錯誤分析。
  • 完成門檻：baseline 與最終方法使用相同測試條件，結果表可由單一命令重建。
  1. 第 13–15 週：壓力測試與處理風險。 至少逐項完成：
  2. 針對「錯誤自動化可能造成全站中斷」建立驗證／檢核方式、緩解措施與停止條件
  3. 針對「控制器競態、權限過大」建立驗證／檢核方式、緩解措施與停止條件
  4. 針對「測試環境難重現真實攻擊」建立驗證／檢核方式、緩解措施與停止條件
  • 完成門檻：每個高風險項都有證據、緩解方式及仍未解決的限制；不得把未知或無效結果隱藏。
  1. 第 15–17 週：整合成可示範成果。 建立從輸入到輸出的固定 demo 腳本，加入錯誤訊息、日誌、逾時／回復與最小操作介面；找未參與開發者照說明操作一次。
  • 完成門檻：5–10 分鐘穩定 demo、備用錄影，以及無網路／模型失敗／裝置斷線時的降級方案。
  1. 第 17–18 週：交付與答辯。 清理 repository，補齊 README、架構圖、資料卡／模型卡、安裝腳本、測試、實驗結果、限制、倫理聲明、簡報與海報；確認不可公開的資料與金鑰未被提交。
  • 完成門檻：另一位同學能依文件重現核心結果，團隊能用一張表回答「比 baseline 好多少、代價是什麼、在哪些條件會失敗」。

R02第 1 週專題負責人R01建立 Git repository、議題看板、每週會議、實驗命名規則與決策紀錄；指派資料／設備、方法實作、評估測試、文件展示四種責任角色。每個後續工作都有一位主責與一位覆核者；README 可說明分支、資料與實驗規則。

R04第 1–3 週資料／設備負責人R01盤點並取得執行第一項核心工作「定義 Custom Resource 與控制迴圈」所需的資料、標註、帳號、API、GPU、感測器或測試設備。同步處理授權、個資、IRB、安全隔離或平台條款。交付資源清單、取得方式、授權證據、資料字典／設備規格及一筆可讀取的真實或合法替代樣資料。
R05第 3–4 週評估負責人R03、R04凍結研究 protocol：研究假設、資料切分、baseline、主要／次要指標、重複次數、統計方法與錯誤分析切片。主要驗證工作必須對應：「以攻擊演練測安全效果、恢復時間與可用性」。在看測試集結果前提交 protocol v1；能從每個研究問題追到一個量測指標與判定門檻。
R06第 3–5 週系統整合負責人R02、R04固定 Go、Kubernetes、Docker、Operator SDK、Istio/Cilium 的版本，建立環境安裝、資料取得／轉換、訓練或建置、評估四個可獨立執行的命令；加入設定檔、隨機種子、日誌與最小測試。在乾淨環境依 README 可從一筆原始輸入產生一筆結果；失敗時回傳明確錯誤而非靜默略過。
R07第 4–6 週方法負責人＋評估負責人R05、R06完成文獻矩陣選定的最簡 baseline，保存設定、執行時間、硬體資源、主要指標與至少 20 個人工檢查案例；不得先調最終方法再回頭挑弱 baseline。單一命令可重建 baseline 結果表；20 個案例均標記成功／失敗原因，並形成錯誤分類表。

R10第 11–13 週方法負責人＋一名覆核者R09實作並驗證核心工作：「以攻擊演練測安全效果、恢復時間與可用性」。先寫最小可測版本，再加入完整資料／場景；每次改動只改一個主要因素並保存設定。交付可執行模組、自動測試、實驗設定與結果；以固定案例證明輸入、輸出及失敗處理符合 scope。

本題完成後，結論應以「以攻擊演練測安全效果、恢復時間與可用性」取得的證據為核心，回答最終方法相對於 baseline 是否改善、改善幅度是否穩定，以及額外付出的運算、資料、設備或人工成本。若主要方法沒有勝過 baseline，也應把負面結果、失敗條件與可重現證據列為有效研究發現，而不是只保留最佳案例。結論還必須明確交代下列限制：錯誤自動化可能造成全站中斷；控制器競態、權限過大；測試環境難重現真實攻擊。在實際測量完成以前，不應填入虛構的準確率、顯著性、使用者療效或安全性宣稱。
